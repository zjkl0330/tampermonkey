# 逆向过程与调试方法

> 这份文档记录「怎么查出来的」，比结论本身更可复用。
> 下次任何一个平台改接口，按这里的方法重跑一遍即可。

---

## 一、判断一个签名算法「是对的还是错的」

不要看返回 200 就以为对了，也不要看报错就以为算法错了。看**错误码有没有往前走一格**。

以迅雷为例：

| 阶段 | 返回 | 判断 |
| --- | --- | --- |
| 不带头 | `invalid_argument: device_id is empty` | 缺参数，不是签名问题 |
| 带 device_id，不带 token | `captcha_invalid: captcha_token is empty` | 继续 |
| 带自己算的 token | `captcha_invalid: 验证码无效` | **还不对** |
| 带页面截获的 token | `200 + share_status: OK` | 页面这条路对 |

再用 Python 复刻同一套 md5 链，拿到 743 字符的 token、请求返回 `200` —— 说明自算算法本身是对的，之前失败是**别的头带错了**。

> 经验：`captcha_invalid` 与「验证码无效」是两个不同分支。前者是「没带」，后者是「带了但校验不过」。

## 二、CORS 排查三步

浏览器报 `blocked by CORS policy` 时，别急着改后端（你也没有后端）。按顺序查：

1. **是不是多带了头**
   打开 DevTools → Network → 那个失败的请求 → 看 `Access-Control-Request-Headers`（预检请求里的）。
   服务端只放行白名单里的头，多一个就全挂。
2. **是不是手写了禁改头**
   `Origin`、`Referer`、`User-Agent`、`Cookie` 在 `fetch` 里是**禁止头**，写了不但无效，某些引擎还会直接判非法。
3. **验证服务端到底放行什么**
   用一条最小请求试：

   ```js
   fetch(url, { headers: { 'x-captcha-token': 'x', 'x-device-id': 'y', 'x-client-id': 'z' } })
     .then(r => r.status)
   ```

   如果这样能拿到业务错误（400 之类），说明头没问题，是你多带了东西。

本次的真实案例：脚本里 `_h()` 带了 `Origin` 和 `X-Client-Version`，两个都不在白名单。删掉后 200。

## 三、`HttpOnly` 导致的「登录了却说没登录」

百度旧版的判断：

```js
ctx.logged = /BDUSS=/.test(cookie) && /STOKEN=/.test(cookie);
```

`BDUSS` 是 `HttpOnly`：

- `document.cookie` 读不到
- `GM_cookie.list` 在多数管理器里也读不到 HttpOnly
- 结果：**用户明明登录了，脚本判成游客**

正确做法（按可靠性排序）：

1. 读页面上下文：`window.locals.dump().loginstate === 1`
2. 发一个同域轻量请求，看回包：
   `GET /api/gettemplatevariable?fields=["bdstoken"]` → 有 `bdstoken` 就是登录态
3. 都失败时，直接把「未登录」当结论并给登录入口，**不要猜**

## 四、识别「化石参数」

特征：接口还在、请求也发得出去、但结果永远不对，而且报错和参数对不上。

百度的 `locatedownload` 就是典型：

```js
'&rand=5ed606e9da222cde0474cdf70eda884b'
'&devuid=0F1E9FC2E084472DA5A61C4CF4C759AF'
'&cuid=0F1E9FC2E084472DA5A61C4CF4C759AF'
'&deviceid=348642637967375013'
'&psign=860a071f77c860e8cea06e4e54c518f3'
'&version=2.2.111.34'
```

`psign` 是某台历史设备算出来的固定值，所有人的代码里都是这一串。它曾经能用，是因为服务端当年不校验；现在校验了，就全废。

**判断方法**：搜一下这串值，如果几十个仓库里一模一样 —— 它一定是抄来的死值，不是算出来的。

**替代路径**：找网页版自己用的接口。打开网页，按 F12 → Network，点一次「下载」，看真实请求打的是谁。百度现在打的是 `api/filemetas`。

## 五、页面上下文探查（Playwright）

很多参数不用逆向，页面自己就有。用 Playwright 打进去 dump 一遍最快：

```python
r = await pg.evaluate("""()=>{
  const dump = window.locals && window.locals.dump ? window.locals.dump() : null;
  return {
    keys: dump ? Object.keys(dump) : null,
    bdstoken: dump && dump.bdstoken ? dump.bdstoken.value : null,
    share_uk: dump && dump.share_uk ? dump.share_uk.value : null,
    jsToken: window.jsToken || null,
    sekey: window.currentSekey || null
  };
}""")
```

百度分享页（游客态）实测输出：

```
loginstate, bdstoken, csrf, uk, username, share_uk, shareid, ...
```

`share_uk` / `shareid` 游客就有，`bdstoken` 为空字符串 —— 这个组合本身就说明了「能列、不能取链」。

## 六、本地 HTTPS 测试台

不改线上接口、不依赖真实分享，自己起一个假网盘：

```python
# server_real.py —— 纯代理，不 mock，避免测试结果被假数据污染
# 关键：allow_redirects=True，否则 CDN 的 302 被吞，下载回来的是空文件
```

启动浏览器时用 host 映射把域名指到本地：

```bash
chromium --host-resolver-rules="MAP pan.quark.cn 127.0.0.1" \
         --ignore-certificate-errors
```

手机环境测试**故意不加** `--disable-web-security` —— 要复现真实 CORS 行为，加了就等于把问题藏起来。

清端口：`fuser -k 443/tcp`。

## 七、踩过的坑（按时间）

| 现象 | 真因 | 处理 |
| --- | --- | --- |
| `GM_xmlhttpRequest is not defined` | 手机脚本管理器没有 GM API | 加兼容层，`typeof GM_xmlhttpRequest === 'function'` 才用，否则 `fetch` |
| 分片下载卡 46% | 不是脚本问题，是 CDN 限速 | 8 路并发直连验证 206 + 哈希一致，确认为限速 |
| OPFS 写完哈希不符 | 测试台代理 `allow_redirects=False`，302 被当成内容 | 改 `True` |
| 139 自动解析失败 | `location.href.split('#')[0]` 把 hash 里的 linkID 截掉了 | 传完整 `location.href` |
| 139 `eNum=300` 报错 | 分页上限 200 | 改 200 |
| 阿里识别不出 | 正则只写 `alipan`，漏了 `aliyundrive` | `/ali(?:pan|yundrive)\.com/` |
| 页面挂两个按钮溢出 | 重复注入 | `data-yx-hooked` 标记 + 只挂一个 |
| `⚡` 显示方块 | 字体缺字形 | 改纯文字「直链下载」 |
| 百度登录了仍提示未登录 | `BDUSS` 是 HttpOnly | 改用 `loginstate` + 接口兜底 |
| 迅雷所有请求 `ERR_FAILED` | CORS 预检被多余请求头打挂 | 删 `Origin` / `X-Client-Version` |
| 百度转存成功但取链失败 | `locatedownload` 的 `psign` 是死值 | 换 `api/filemetas` |

## 八、可复用的验证顺序

拿到一个陌生平台时，按这个顺序走，每步都能独立证伪：

1. **打开分享页，F12 Network** —— 看页面自己打了哪些接口，这是最权威的协议文档
2. **curl 复刻最简请求** —— 去掉所有自定义头，只留必需参数，确认能通
3. **逐个加头** —— 每加一个测一次，找到最小可用集合（这一步能直接定位 CORS 白名单）
4. **dump 页面变量** —— 能用页面给的就不自己算
5. **真要算签名时，用两种语言各实现一遍** —— 结果一致才说明算法对，不然是巧合
6. **端到端** —— 注入脚本、点按钮、看文件真的下下来、比对哈希

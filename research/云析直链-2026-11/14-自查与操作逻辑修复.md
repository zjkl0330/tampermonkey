# 14 · 自查：5 个操作逻辑问题与验证（v1.16.0）

> 起因：功能补到 6 家个人盘后，回头系统查了一遍「操作逻辑」。查出 5 个会让用户真踩到的问题，
> 都不是新功能缺失，而是行为不一致 / 状态没管住。每个都写了复现路径和验证方式。

## 一、批量操作与搜索的作用域不一致

**现象**：勾 10 个文件 → 搜索「abc」（列表只剩 2 行）→ 点「复制已选」→ 复制出 10 条，
其中 8 条是用户在屏幕上根本看不见的。

**原因**：`selectAll()` 用 `visibleItems()`（筛选后），`copySelected()` / `downloadSelected()` 用 `state.items`（全量）。

**修法**：统一到 `selectedFiles()`，只返回「当前可见且已选」；
被跳过的数量明确提示，并把状态栏改成「已选 3（筛选内 1）」，避免「已选 12 配 2 行列表」的错觉。

```js
function selectedFiles() {
  const visible = new Set(visibleItems().filter((i) => !i.dir).map((i) => i.fid));
  const all = state.items.filter((i) => !i.dir && state.selected.has(i.fid));
  return { targets: all.filter((i) => visible.has(i.fid)), hidden: all.length - targets.length };
}
```

**验证**：`test_batch_scope.py` — 3 个文件全选 → 搜 `a.mkv` → 下载已选，
断言取链请求只有 `[['f1']]`，且出现「已跳过搜索范围外的 2 个已选文件」。

## 二、直链缓存永不过期

**现象**：面板挂两小时不动，再点「复制」拿到的是死链；百度尤其明显（dlink 8 小时）。
用户看到的是「链接打不开」，不会想到是缓存。

**修法**：缓存存 `{link, at}`，读取时按 15 分钟 TTL 判断，过期自动重取。
平台可以覆盖（`platform.linkTTL`），但暂时没有平台需要。

**验证**：`test_link_ttl.py` — 用 Playwright 的 `clock.set_system_time` 推进 16 分钟，
断言取链请求次数从 1 变 2，剪贴板里的链接序号从 `1` 变 `2`（第一次与第二次都是 `1`，说明缓存命中）。

```
第一次复制后，取链请求数: 1
第二次复制后（应命中缓存）: 1
推进 16 分钟后再复制（应重新取链）: 2
链接序号: ['1', '1', '2']
```

## 三、递归下载会瞬间铺开几百条连接

**现象**：200 个文件的目录点「全下」，`enqueueFiles` 一口气 `DL.start()` 全部任务；
每个任务 `threads = max(2, 8/running)`，即使 running 很大也至少 2 条 → 总连接数无上限。

**修法**：加 `DL_MAX_RUNNING = 3` + 显式的 FIFO 队列：

```js
if (this.liveCount() > DL_MAX_RUNNING) {
  task.queued = true;
  DL_QUEUE.push(fid);
  while (task.queued && task.status === 'probe' && this.tasks.get(fid) === task) await sleep(300);
}
```

`release()` 在 finish / fail / pause / cancel / start 失败分支调用，每次只放行一个。

**踩到的坑**：第一版用 `while (activeCount() >= 3) sleep`，实测出现 **4 个任务同时在跑**。
因为 `activeCount()` 只统计 `status === 'run'`，probe 阶段不计入，多个任务在探测期一起越过阈值。
改成 `liveCount()`（probe + run，排除 queued）+ 显式队列后才稳定。

**验证**：`test_dl_queue.py` — 6 个文件、CDN 每个分片延迟 3 秒，9 秒时统计按钮文案，
稳定得到 3 个「暂停」+ 1 个「排队」，状态栏「⬇ 2/6 排队 1」。连跑 3 次结果一致。

> 顺带踩到 CORS 的一个规范细节：`Access-Control-Expose-Headers: *` 在带 credentials 的请求里
> **不作为通配符**，必须显式列出 `content-range, accept-ranges`，否则 `probe()` 读不到 Range 头，
> 会误判「不支持分片」降级成单连接。这不是脚本 bug，但值得记一笔 —— 真实 CDN 不走 CORS（GM 通道），
> 只有打桩时会撞到。

## 四、大目录递归：扫完直接排队，用户等不到结果

**现象**：扫到 200 个文件后全部进下载队列，浏览器里排 200 个任务，既慢又容易被拦；
而且文件名平铺，两个子目录里的 `1.mp4` 会互相覆盖。

**修法**：
- 扫到 > 20 个直接改导出 Aria2 清单（`exportAria2List`），不进队列；
- `walkFolder` 给每个文件带 `rel`（相对路径），导出时 `mkdir -p` + `-d/-o` 分隔；
- DL 里用 `saveName`（路径的 `/` 换成 `_`），浏览器下载的同名文件也能区分。

**验证**：`test_folder_export.py` — 25 个文件的目录，断言脚本里有 `mkdir -p "相册"`、
`-d "相册" -o "1.mp4"`、25 条 `aria2c`。

## 五、扫描期间切目录不会中止

**现象**：点「全下」后立刻点进另一个文件夹，扫描还在后台按旧队列跑，
最后把旧目录的文件塞进新列表的下载队列。

**修法**：加 `scanSeq` 计数器，`enterDir` / `backDir` / `reloadMine` 各自 `scanSeq++`；
`walkFolder` 每轮检查 `token !== scanSeq` 就抛「目录已切换，扫描中止」。
同时 `scanning` 标志防连点（两条扫描并发会让请求翻倍）。

## 六、顺手改的两处

| 改动 | 原因 |
| --- | --- |
| 分享页不再显示「全下」 | 分享页取链依赖 stoken / fids_token，递归子目录后是否成立无法在无真实账号时确认。分享页仍可进目录 → 全选 → 下载已选 |
| 状态栏显示「⬇ 2/6 排队 1」 | 递归下载的文件没有行，行内进度看不到；批量下载时用户需要知道总体在动 |
| 浏览器直下模式上限从 20 降到 5 | 连续 `window.open` 到第五六个就被浏览器拦，给 20 个只会让用户以为「点了没反应」；分片模式仍是 20 |

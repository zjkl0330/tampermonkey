# 08 · 更新源可用性实测（2026-11-14）

## 起因

v1.9.0 把自动更新挂到了 `raw.githubusercontent.com`，但用户侧反复出现「检查更新失败」。
本次在同一台国内出口的沙箱里，对同一文件做了多源对照：限速、CORS、缓存行为。

## 结论先行

| 源 | 首字节量级 | `Range` 支持 | `ACAO` | 版本新鲜度 | 结论 |
| --- | --- | --- | --- | --- | --- |
| `raw.githubusercontent.com` | 0.8~1.4s，但约一半请求直接握手超时（30s 无响应） | 206 ✓ | `*` | 最新 | 首选，但不稳 |
| `ghproxy.net` | 0.6s | 206 ✓（`content-range: 0-2047/204351`） | `*` | 最新 | 第一兜底 |
| `ghfast.top` | 2.4~7.3s | 206 ✓ | `*` | 最新 | 第二兜底 |
| `cdn.jsdelivr.net` | 0.6~2.3s | 206 ✓ | `*` | **落后一个版本** | 只作末位 |
| `api.github.com`（contents） | 2.2s | — | `*` | 最新 | 共享出口 IP 下 60/h 配额被打满，实测 403 / `x-ratelimit-remaining: 0`，不可用 |
| `cdn.statically.io` | 15s 超时 | — | — | — | 不可用 |
| `raw.gitmirror.com` | 立即失败 | — | — | — | 域名解析不到，不可用 |

## 关键发现：jsDelivr 的分支缓存不会因 purge 立即失效

```
POST https://purge.jsdelivr.net/gh/zjkl0330/tampermonkey@main/js/云析直链.user.js
→ {"status":"finished","providers":{"CF":true,"FY":true}}
```

purge 返回 finished、CF 与 FY 都标记为已清，但紧接着（0.6s、20s、60s 后）从 `cdn` 与 `fastly`
两个节点取回的文件仍是旧版：

```
cdn:    HTTP 200  2.3s  @version 1.9.2  md5 ead749a4...
fastly: HTTP 200  2.1s  @version 1.9.2  md5 ead749a4...
```

即分支引用（`@main`）在 jsDelivr 上是按「解析后的 commit」缓存，purge 清的是给定路径的键，
新 commit 的映射本身要等回源才更新，最长 12 小时。**把它当唯一兜底，用户会在 12 小时内看不到新版** ——
这正好抵消了「raw 不通所以要兜底」的目的，所以最终把反代排在它前面。

附带一条：`?t=123` 这类 query 不影响 jsDelivr 的缓存键，实测返回同一 md5，不能用来破缓存。

## 最终实现（v1.9.3）

```
raw（6s）→ ghproxy.net（8s）→ ghfast.top（8s）→ jsDelivr（8s，标记 lag）
```

- 每个源都发 `Range: bytes=0-2047`（CORS 安全头，不触发预检），只解析脚本头里的 `@version`；
- 面板状态行实时显示「正在检查更新…（当前源名）」，不是干等；
- 命中 `lag` 源且无新版时，文案改成「已是最新（CDN 缓存，最多滞后 12 小时）」，不假装权威；
- 全失败时把四个源各自的错误拼起来抛（超时 / HTTP 码 / 无 `@version` 可区分）；
- 反代只用来**读版本号**，安装与更新仍走 `@updateURL` / `@downloadURL` 的原始地址，
  不会把第三方反代返回的正文当脚本执行。

`@connect` 同步加了 `ghproxy.net`、`ghfast.top`，删掉不再使用的 `fastly.jsdelivr.net`。

## 浏览器内验证

用 Playwright 把脚本注入到 `https://pan.quark.cn/s/test`（路由伪造页面），两条路径都实跑：

1. **正常**：raw 通，0.5s 内返回 `已是最新版本 v1.9.3（源：GitHub raw）`。
2. **掐 raw**：`route('https://raw.githubusercontent.com/**', abort('timedout'))`，
   页面侧真实报 `net::ERR_TIMED_OUT`，随后自动落到 `ghproxy.net`，同样拿到 v1.9.3，
   提示 `已是最新版本 v1.9.3（源：ghproxy.net）` —— 说明反代的 `ACAO: *` 在真实页面上下文里有效，
   不是 curl 才通。

## 遗留

- 反代是公共设施，随时可能挂或改行为；四个源里挂了两个不影响（raw 与另一个反代互为备份），
  但若长期只剩 jsDelivr，就得考虑换自有反代（`gh.zjkl0330.dpdns.org` 目前无 CORS，浏览器读不了）。
- 未在真实国内 4G 网络下复测（沙箱出口有代理），延迟数字仅供参考量级。

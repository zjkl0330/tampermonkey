# 13 · 整目录下载与本地排序（v1.15.0）

> 起因：上一轮盘点剩两件事——「整目录递归下载」和「服务端排序」。
> 第一件照做；第二件做成了**本地排序**，原因写在第三节，不是偷懒。

## 一、整目录递归下载

面板里文件夹行原来只有「进入」，要下整个文件夹只能一层层点进去、逐个勾。

现在文件夹行多一个「全下」：BFS 逐层列目录，把里面所有文件收进来，再走批量下载队列。

```js
const queue = [{ fid: root.fid, depth: 0 }];
const seen = new Set([String(root.fid)]);   // 防环：个别平台能构造出目录环
while (queue.length) {
  const cur = queue.shift();
  const list = await state.platform.list(state.ctx, cur.fid);
  for (const it of list) { ... }
  if (queue.length) await sleep(120);
}
```

三条硬限制，都是为了别把风控招来：

| 限制 | 值 | 理由 |
| --- | --- | --- |
| 深度 | 8 层 | 目录树动辄几十层的话，光扫描就够触发风控 |
| 文件数 | 200 | 再多就该用「导出 Aria2」，浏览器里排队取链不现实 |
| 扫描间隔 | 120ms | 每层列目录之间歇一下 |

截断不是静默的：`toast` 会明确写「文件超过 200 个，只取前 N 个」。

### 踩到的坑：脚本会被自己的请求带跑

第一次测出来扫描了 `['0', 'd1', 'd2', 'd2']`——`d2` 多了一次。

原因是 `hookMineDir` 劫持了 `fetch` / `XMLHttpRequest.open`，用来跟随「页面自己在切目录」。
但**脚本自己在无 GM 环境下的请求也走 `fetch`**，于是自己的 `sort?pdir_fid=d2` 被自己当成页面导航，
`pageMineDir` 变成 `d2`，`followMineDir` 又列了一次，面板还会跟着跳。

修法：加一个 `scanningFolder` 标志，扫描期间 `grab()` 直接 return。
比「给请求打标记」简单，也不会漏掉其他调用点。

```js
const grab = (u) => {
  if (scanningFolder) return;   // 递归扫描时不做页面跟随
  ...
};
```

改完扫描序列变成 `['0', 'd1', 'd2']`，每个目录恰好一次。

## 二、排序：为什么是本地排

先说结论：**排序按钮只排已经加载到面板里的条目，不往接口塞 sort 参数。**

六种循环：名称 ↑ / 名称 ↓ / 大小 ↓ / 大小 ↑ / 时间 ↓ / 时间 ↑。文件夹恒在最前（文件管理器惯例）。

排序键：

- `name`：`localeCompare(..., 'zh-Hans-CN', { numeric: true })`，所以「第2集」排在「第10集」前面；
- `size`：数字比较；
- `mtime`：统一转成毫秒时间戳比较。

`mtime` 是这次新加的字段，各平台来源不同：

| 平台 | 字段 | 格式 |
| --- | --- | --- |
| 夸克 / UC | `updated_at` | unix 秒 |
| 123 | `UpdateAt` | `"2026-11-14 23:00:00"` |
| 百度 | `server_mtime` | unix 秒 |
| 迅雷 | `modified_time` | ISO 串 |
| 城通 | `mtime` / `updated_at` / `modified` / `create_time` 依次尝试 | 未知 |

统一走 `toMs()`：数字按「>1e12 是毫秒，否则是秒」，字符串先试纯数字再 `Date.parse`，
解析不出来返回 0（排到最后），不让异常值污染列表。

## 三、为什么不做服务端排序

各家个人盘的排序参数：

| 平台 | 参数 | 取值 | 是否验证过 |
| --- | --- | --- | --- |
| 夸克 / UC | `_sort` | `file_type:asc,updated_at:desc` | 只见过这一个值，其他取值没验证 |
| 123 | `sortBy` / `sortDirection` | 未知 | 没验证 |
| 百度 | `order` / `desc` | 从分享页看到 `order=name` | 个人盘没验证 |
| 迅雷 | `order`? | 未知 | 没验证 |
| 城通 | `sort`? | 未知 | 没验证 |

没有真实账号，这些参数全是「看起来对」。塞进去最坏的结果不是报错，而是**静默失效**——
按钮切到「大小 ↓」，列表纹丝不动，用户以为脚本坏了。

本地排序没有这个问题：行为完全可预测，一页 100 项以内（各平台单页上限：夸克/UC 100、
123 100、百度 1000、迅雷 100、城通 100）足够用。超过一页的目录，排序只作用于已加载部分——
这点在文档里写明了，不装。

## 四、验证

新增两个用例，都是打桩：

| 用例 | 断言 |
| --- | --- |
| `test_quark_dir_dl.py` | 点「全下」后扫 `['0','d1','d2']` 各一次（`d2` 不得重复）；`d1` 里的 `f2` 与 `d2` 里的 `f3` 都被下载 |
| `test_quark_sort.py` | 六次点击的顺序依次为 名称↑/名称↓/大小↓/大小↑/时间↓/时间↑，第六次回到起点且按钮文案同步 |

顺带发现的回归：排序把文件夹提到最前后，三个旧用例「点第一个 checkbox」正好点到文件夹的
disabled checkbox，复制失败。这不是功能 bug，是测试假设过期——选择器改成
`input[type=checkbox][data-fid]:not([disabled])`。

## 五、仍未闭环

- 递归下载在超深 / 超大目录下的真实表现（限深 8 层、限 200 个文件是保守值，没在真实盘上试过）；
- 城通的时间字段用多候选兜底，实际命中哪个还得看真实回包；
- 分页超过一页时本地排序只覆盖已加载部分，没有做「滚动到底自动加载更多」。
